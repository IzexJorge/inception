# Inception

## Description

Inception is a system administration project, which goal is to build with Docker Compose a web infrastructure, composed of three Docker containers that communicate with each other through a Docker network.  
A container is a process that uses the Linux kernel functions to isolate its own processes, network and file system. Each container is created from a Docker image.  
An image is a template that presents everything needed for the container to initialize, including the script that is executed every time the container starts or restarts.  
An image is built from a `Dockerfile`, a text file with commands that define layers that only need to be rebuilt if a previous layer has been rebuilt because of a modification.  
All Dockerfiles in this project have been written specifically for it, and the only ready-made component they use is the penultimate stable version of Debian, which is the starting point of each of the three containers.  
Each container runs a service that is required for our web infrastructure to work properly.  
Our infrastructure uses two volumes, whose data is located at `/home/<login>/data/` in the host and mounted in the containers. This data survives after deleting the containers and the images.

### NGINX

NGINX is the web server that receives the requests sent by the visitors' browsers and sends back the answers.  
Its container is the only part of the infrastructure that can be reached from outside, through the host's port 443, the standard one for secure web connections (HTTPS).  
It uses a self-signed certificate for the HTTPS' TLS encryption, which means browsers cannot verify it with any authority and show a warning that has to be accepted manually.  
NGINX also acts as a reverse proxy, sending requests (FastCGI protocol) to the WordPress container whenever a visitor's request requires generating an HTML page.  
It shares a volume with the WordPress container, which holds the WordPress files and allows it to directly manage any data that doesn't need to be generated by the WordPress container.

### WordPress

WordPress is a PHP application for creating and managing websites. Through its administration panel, the owner can manage the website without programming.  
PHP-FPM is the PHP FastCGI Process Manager that runs WordPress. It interprets the FastCGI requests from NGINX and responds back with HTML code.  
To build HTML pages, WordPress asks for data stored in a database, managed by MariaDB in the third container.

### MariaDB

The database is stored in a volume, which is not accessible from the other two containers, and it's managed by a MariaDB server that runs in this container.

## Project description

### Use of Docker

- Each service has its own `Dockerfile` in `srcs/requirements/<service>/`. They start from the penultimate stable version of Debian.
- Images are named after their services and are built by Docker Compose using the file `srcs/docker-compose.yml`.
- All containers are attached to a user-defined bridge network and restart automatically after a crash.
- The `Makefile` at the root is the single entry point: it prepares or validates what docker compose needs, provides wrappers for its most important commands and allows to easily clean either with or without deleting the persistent data.
- Non-sensitive configuration is injected through `srcs/.env`, and passwords through Docker secrets.

### Main design choices

- **One service per container.** Each container runs a single daemon and nothing else: `nginx`, `php-fpm` and `mariadbd`.
- **Daemons run in the foreground as PID 1.** Each entry-point script ends with `exec`, replacing the shell with the daemon. Docker signals therefore reach the daemon directly and `docker stop` shuts it down cleanly. There are no `tail -f` tricks, `sleep infinity`, infinite loops or wrapper supervisors such as `mysqld_safe`, so restarts are handled by Docker.
- **Initialisation happens at start, not at build.** Anything that needs a volume, a secret or another container is done by the entry-point scripts: database bootstrap, WordPress installation with WP-CLI and certificate generation. Scripts are idempotent, and every wait for a dependency has a bounded number of retries and fails with an explicit error.
- **TLS.** `nginx` generates a self-signed certificate when it starts, with the domain name as Common Name (CN), so the private key is never stored in an image layer. Only TLSv1.2 and TLSv1.3 are enabled. Browsers show a warning because the certificate is self-signed, which is expected.
- **Single entry point.** Only `nginx` publishes a port, and the host port is fixed at 443. The port each service listens on inside its container is configurable in `srcs/.env`. NGINX issues relative redirects so URLs stay correct whatever its internal port is.
- **Fail-fast Makefile.** It aborts with a clear message if `srcs/.env` is missing, a required variable is empty, or the WordPress administrator name contains `admin`.
- **Readable logs.** The NGINX and php-fpm logs are redirected to stdout/stderr, so `docker compose logs` shows everything.

### Comparisons

#### Virtual Machines vs Docker

A virtual machine emulates hardware and runs a complete operating system with its own kernel on top of a hypervisor. It offers strong isolation but is heavy: gigabytes of disk and minutes to boot.  
A container shares the kernel of the host and is isolated with namespaces (PID, network, filesystem...) and cgroups (resources control). It is much lighter, starts in seconds, and an image built from a Dockerfile is reproducible and portable. The trade-off is weaker isolation, because the kernel is shared.

#### Secrets vs Environment Variables

A secret is sensitive information that mustn't ever be shared by the repository, nor be present in an image or in the environment. They are created by each user as text files in `secrets/` and used by Docker Compose through Docker secrets.  
Environment variables are non-sensitive user data, or just data that the user might want to change. They are defined by the user in `srcs/.env`, which the user creates by copying and renaming `srcs/.env.example`, which acts as a template, since it doesn't make sense to include the `srcs/.env` in the repository, as some of the values aren't adequate for any user. They are used by Docker Compose through the env_file parameter.

#### Docker Network vs Host Network

On a Docker bridge network, containers get private addresses and an embedded DNS server that resolves service names to container IPs. Nothing is reachable from outside unless a port is published, and only `nginx` publishes one.  
With the host network a container shares the network stack of the machine, so every listening port is exposed and port clashes are possible.

#### Docker Volumes vs Bind Mounts

A bind mount maps a specific host path to a path inside a container, allowing direct access, but it does not create a Docker volume resource.  
A Docker volume is a resource managed by Docker that has a lifecycle independent of the containers using them.  
By default, Docker stores volumes data in `/var/lib/docker/volumes/`. However, the Docker named volumes in this project use the `driver: local` configuration with `type: none`, `o: bind` and `device: /home/<login>/data/...` options, which allows them to be mapped to a host path.

## Instructions

The instructions are split by audience:

- `DEV_DOC.md` — Developer documentation. Describes how a developer can:
	- Set up the environment from scratch (prerequisites, configuration files, secrets).
	- Build and launch the project using the Makefile and Docker Compose.
	- Use relevant commands to manage the containers and volumes.
	- Identify where the project data is stored and how it persists.
- `USER_DOC.md` — User documentation. Explains how an end user or administrator can:
	- Understand what services are provided by the stack.
	- Start and stop the project.
	- Access the website and the administration panel.
	- Locate and manage credentials.
	- Check that the services are running correctly.
